# 狼黑工具 · 实机测试与缺陷报告（v1.17.6）

> 测试时间：2026-10-21
> 被测版本：`wolfblack-tool` v1.17.6（`package.json` / `extension.json` / CHANGELOG 三处一致）
> 测试方式：**双客户端实机对照**（同一 PCB 文档同时在 V2.2 与 V4 打开）+ 静态审查 + 受控写入回放
> 测试通道：EDA 桥（`tools/eda-bridge/server.mjs`），端口 `2245` → V2.2.45.5、`4178` → V4.1.78

## 二、结论摘要

**功能面基本可用**：79 个被调用的 `eda.*` API 路径中，**78 个在两个版本都存在**；`create` 实参顺序与官方类型声明一致，写入后读回的数值一致；V4 的网表新格式（`{version, projectId, components}`、`pinInfoMap`）在 5 个页面里都已适配。

**但有 4 个 P0 级缺陷**：其中 1 个可能**写坏文档**、1 个让 **V4 全部快捷键失效**、2 个让**导线⇄线条转换留下残影或丢数据**。

| 级别 | 数量 | 概要 |
| :--- | :-: | :--- |
| **P0 立即修** | 4 | 跨文档写入风险、V4 快捷键全失效、Region 删不掉、先删后建丢数据 |
| **P1 短期修** | 6 | V4 器件名取空、BOM 写入不生效、弧线角度倍率用错、假成功状态、刷新 API 不存在、源码写回丢铜皮缓存 |
| **P2 择机修** | 6 | 网表读取无判空、桥建图元未 await、焊盘 pasteMask 语义、校准无版本维度、桥只支持单客户端、V4 尺寸量化 |

## 三、P0 · 立即修

### P0-1 · 「从 PCB / 网表创建导线」可能把导线源码写进 **PCB 文档**

**位置**：`src/js/autoWire/index.js:204-237`（切换）、`:84`（读源码）、`:151`（写回）

```js
// :231 切换回原理图
async function switchToSchematic() {
    try {
        await eda.dmt_EditorControl.activateDocument(_lastSchematicTabId);  // 可能为 null
    } catch (error) {
        console.error('切换原理图失败:', error);   // ← 静默吞掉，流程继续
    }
}
// :84 之后才读源码 —— 此时可能仍在 PCB 文档上
let documentSource = await eda.sys_FileManager.getDocumentSource();
...
await eda.sys_FileManager.setDocumentSource(documentSource);   // :151 写进当前文档
```

**为什么危险**：`_lastSchematicTabId` 只有在 `switchToPCB()` 里「当前文档 documentType === 1（原理图）」时才被赋值（`:202-207`）。若用户从 PCB 侧触发、或分屏信息异常，它就是 `null`；`activateDocument(null)` 抛错 → 被 catch 吞掉 → 后续**读到的是 PCB 源码**，再把 `{"type":"WIRE"...}` / `["WIRE",...]` 追加进去写回 PCB。PCB 里混入原理图图元行，属于**结构性写坏**。

**修复建议**（约 15 行）：

```js
async function switchToSchematic() {
    if (!_lastSchematicTabId) throw new Error('未能定位原理图页签，已中止（避免写入错误文档）');
    await eda.dmt_EditorControl.activateDocument(_lastSchematicTabId);
}
// 写入前再自检一次
const cur = await eda.dmt_SelectControl.getCurrentDocumentInfo();
if (!cur || cur.documentType !== 1) throw new Error('当前文档不是原理图，已中止写入');
```

> 同类自检也建议加在 `PcbToSch`（`iframe/js/app/PcbToSch.js:465` 附近），它同样是「读当前文档 → 拼源码 → 写回当前文档」。

### P0-2 · V4 下 **所有快捷键失效**

**位置**：`src/index.ts:207`

```ts
if (editorVersion.trim().startsWith('3.')) {   // ← V4 不匹配
    // 导入图片 Ctrl+Shift+C / 导线⇄线条 Ctrl+Shift+X /
    // 焊盘⇄过孔 Ctrl+Shift+G / 填充⇄图片 Ctrl+Shift+F
}
```

**实测**（V4.1.78 客户端）：`getEditorCurrentVersion() = "4.1.78"`，`.startsWith('3.') = false`，`sys_ShortcutKey.getShortcutKeys()` 返回空数组，且 `sys_ShortcutKey.registerShortcutKey` 在 V4 **确实存在**（可注册）。

**为什么漏了**：v1.17.4 已把「写源码/选解析器」的版本判断统一改成 `isModern()`，但入口文件这段是后端 TS，没走公共模块，仍是裸 `startsWith('3.')`。

**修复建议**：

```ts
const major = Number(editorVersion.trim().split('.')[0]);
if (major >= 3) { ... }        // V3 / V4 都注册
// 或 V4 新增的便捷方法：eda.sys_Environment.isEditorCurrentVersionGreaterThanOrEqual('3.0.0')
```

### P0-3 · 导线⇄线条：**Region 用错删除 API，删了等于没删**

**位置**：`src/js/WireConverter.js:157`

```js
await eda.pcb_PrimitivePolyline.delete(regionItem.primitiveId);   // ← Region 却调 Polyline
```

**实测**（V4.1.78，同一个真实 Region `8ec6eaee714ef6c8`）：

| 操作 | 返回值 | 对象是否还在 |
| :--- | :--- | :--- |
| `pcb_PrimitivePolyline.delete(regionId)` | **`true`** | **在**（`pcb_PrimitiveRegion.get()` 仍能取到） |
| `pcb_PrimitiveRegion.delete(regionId)` | `true` | 不在 |

**影响**：选中「区域」执行「导线⇄线条」后，会**同时存在**新的导线和原来的区域（视觉重叠、网表/DRC 出现重复几何），而且接口返回 `true`，`catch` 也不会触发告警。

对照：`src/js/RegionImageConverter.js:345` 用的就是正确的 `eda.pcb_PrimitiveRegion.delete`。

**修复**：`await eda.pcb_PrimitiveRegion.delete(regionItem.primitiveId)`。

### P0-4 · 导线⇄线条：**先删后建**，一旦创建失败原图元就没了

**位置**：`src/js/WireConverter.js:131`（折线）、`:157`（区域）、`:289-291`（直线/弧线）

```js
await eda.pcb_PrimitivePolyline.delete(polyItem.primitiveId);   // 先删
await this._emitLinesFromPath(...);                            // 再建；中途失败 → 原图元已不可恢复
```

**影响**：非铜层/参数异常/API 抛错时，用户的线条变成「既没有原图元、也没生成导线」。这类操作没有撤销栈保护（走源码/API 直改），风险高于「多一步」。

**修复**：改成「先建 → 全部成功再删」，与 `PadViaConverter` 的处理保持一致（它是 `if (newVia) { await delete(...) }`，写法正确）；失败时回滚已创建的新图元并提示。

## 四、P1 · 短期修

### P1-1 · 「批量替换器件」在 V4 下**器件名列是空的**

**位置**：`iframe/js/app/ReplaceComponent.js:130`

```js
const deviceName = props["Device"] || comp.manufacturerId || "";   // V4 两者都没有
```

**实测**（同一块板，`pcb_PrimitiveComponent.getAll()`）：

| 位号 | V2.2 `otherProperty.Device` | V4 `otherProperty` 里 | V4 可取到器件名的位置 |
| :--- | :--- | :--- | :--- |
| C1 | `CAP_0603` | **无 `Device` 键** | `comp.component.uuid.name` = `CAP_0603` |
| Q1 | `AO3401A_P` | 无 | `comp.component.uuid.name` = `AO3401A_P` |
| R1 | `Res_0603` | 无 | `comp.component.uuid.name` = `Res_0603` |

**连带影响**：`comp.name` 在 V4 是模板串 `"={Value}"`（V2.2 是字面值 `"100nF"`）。`resolveDynamicString` 能靠 `otherProperty.Value` 解析出 `100nF`（这一步是对的），但 **Q1 这类 Name 为空的器件没有兜底**：V2.2 显示 `AO3401A_P`，V4 显示空白 —— 表格里两个不同器件可能被合并成同一组，替换目标就会错。

**修复**：

```js
const deviceName = props["Device"]
    || (comp.component && comp.component.uuid && comp.component.uuid.name)   // V4
    || (comp.component && comp.component.name)
    || comp.manufacturerId || "";
```

### P1-2 · 「导入 BOM」只写 `Name`，V4 画布显示不更新

**位置**：`iframe/js/app/ImportBom.js:392`

```js
comp.props.Name = item.name || item.original.name;   // 只写 Name
// 缺：comp.props.Value = ...
```

**原因**：V4 里器件的「Name」属性值是 `={Value}`（引用 Value 属性），源文件与 `getAll()` 都能看到：

```
V2.2  ATTR ... "key":"Name","value":"100nF"      ← 字面值
V4.1  ATTR ... "key":"Name","value":"={Value}"   ← 模板引用
```

所以 V4 下把 `props.Name` 改掉，画布上（以及后续按 Name 取值的逻辑）看到的仍是 `Value` 的旧值 → 用户会觉得「导入成功但没变化」。

**修复**：两版都写 `Value`，`Name` 仅在非模板时写：

```js
comp.props.Value = item.name || item.original.name;
if (!/^=\{.*\}$/.test(String(comp.props.Name || ''))) comp.props.Name = comp.props.Value;
```

### P1-3 · 弧线角度校准倍率**用在了错的一侧**，会把圆弧压直

**位置**：`src/js/WireConverter.js:279`（Arc→Polyline）、`:125`/`:149`（Polygon→Arc）

```js
const angleScale = api["获取弧线"]?.["圆弧角度"] ?? 1;   // 用于「写入」多边形
const angle = wireItem.arcAngle * angleScale;
polygonArr = [startX, startY, 'ARC', angle, endX, endY];
```

**实测单位（两版一致）**：
- `pcb_PrimitiveArc.create(..., 90, ...)` → `get()` 回来 `arcAngle = 90`；
- 多边形路径 `["ARC", 90, x, y]` 写入后读回仍是 `90`，官方类型声明也写明「角度制」（`index.d.ts:16285`）。

**问题**：这段把「**读取**侧的倍率」乘到了「**写入**多边形」上；而当前 V4 客户端的校准数据里正好存着：

```json
"获取弧线": { "坐标": 1, "线宽": 1, "圆弧角度": 0.017453 }
```

`0.017453 = π/180`。于是把一段 90° 圆弧转成线条时，写进多边形的角度变成 `90 × 0.017453 ≈ 1.57`，**圆弧几乎变成直线**（角度越小，弦越直）。这不是理论风险：配置已经在客户端里了，只要用户选中弧线点一次「导线⇄线条」就会复现。

**修复**：
1. 弧线角度两侧同为角度制 → **不应用任何倍率**（删掉 `angleScale`）；
2. 若保留校准能力，必须做数值合法性校验（如 `0.5 ≤ k ≤ 2`），并在 APITest 里写明单位；
3. 顺手把 `获取弧线` / `创建弧线` 的语义在 UI 上标注清楚（一个是读、一个是写）。

### P1-4 · 「生成物理网络」API 方式：`modify` **没 await**，状态全显示「完成」

**位置**：`iframe/js/app/GenerateNet.js:1543-1552`

```js
case "VIA":  eda.pcb_PrimitiveVia.modify(op.id, props); break;   // 无 await
...
success = true;                                                   // 立即置成功
} catch (e) { success = false; ... }                              // 异步失败捕不到
```

**后果**：
- 任何一条失败都会被记成「完成」，用户看到 100% 绿条但网络没改；
- 拒绝的 Promise 变成 unhandled rejection（控制台报错、无法定位是哪一条）；
- 成百上千条同时发出（循环无节流），可能压爆 RPC 通道。

**实测**：`pcb_PrimitiveVia.modify(id, {net:'GND'})` 用 `await` 调用可在两版正常返回；`pcb_PrimitivePad.modify` 在 V4 也返回对象（V2.2 仍是代码里注明的「待官方修复」）。

**修复**：逐个 `await`（并保留 BATCH_SIZE 的让步），按返回值/异常统计成功数，最后汇总「成功 N / 失败 M」。

### P1-5 · `eda.sys_Window.redraw()` **两个版本都不存在** → 写完源码画布不刷新

**位置**：`iframe/js/app/GenerateNet.js:1517`、`:1587`

**实测**（`probe` 指令逐段下钻）：`eda.sys_Window` 存在，但 `redraw` 在 V2.2.45.5 与 V4.1.78 **都是 `MISSING@redraw`**。

所以两处 `try { eda.sys_Window.redraw(); } catch(e){}` 是「永远抛错 + 永远被吞」，等于什么都没做。用户感觉是「写入成功了，但画面还是旧的，要自己切页签才刷新」。

**修复**（按可用性择一）：
```js
await eda.pcb_Document.save();                 // 两版都有
await eda.dmt_EditorControl.zoomToAllPrimitives();  // 或触发一次视图重算
```
（`sys_Window` 在 V4 只有 `open/openUI/urlPushState/getViewportSize` 等，没有重绘入口。）

### P1-6 · 整份源码写回，在 **V4 会丢掉 `POURED`（铜皮填充）行**

**实测**（V4.1.78，写回客户端自己刚读出来的源码）：

| 项 | 写回前 | 写回后 |
| :--- | ---: | ---: |
| 源码长度 | 45,557 | **43,119** |
| `POURED` 行 | 2 | **0** |
| 其余行 | — | 完全一致（仅 DOCHEAD 时间戳变化） |

同一操作在 V2.2.45.5 上：**逐字节一致**（14,368 → 14,368，`POURED` 8 行保留）。

**影响**：`POURED` 是铜皮「已计算填充」的几何缓存（`POUR` 本体还在，`pcb_PrimitivePour.getAll()` 仍是 2 个）。整份写回后缓存被清空，**铜皮显示/DRC 需要重新计算**才算恢复；在重算之前，用户可能看到「铜皮空了」。凡是整份重写源码的功能都在影响面内：`生成物理网络（源码方式）`、`从PCB转原理图`、`批量修改网络` 的源码分支。

**修复建议**：
1. 优先「只替换需要改的那几行」，保持其余行原样（`GenerateNet` 已经是逐行改写，问题在它把**整篇** `setDocumentSource` 回去——这一点本身无法避免，但可以把 `POURED` 行原样带上并验证是否被接受）；
2. 写回后主动触发一次铜皮重算（若 API 可用），或在 UI 明示「已修改，请重算铜皮」；
3. 在测试里加一条「写回后 `POURED` 行数不减少」的断言（现有样本测试只比对行内容，没有实机写回）。

## 六、实测确认「没问题」的部分（避免误改）

| 检查项 | 结论 |
| :--- | :--- |
| 代码中调用的 79 个 `eda.*` 路径 | **78 个两版都存在**；唯一缺失是 `sys_Window.redraw`（见 P1-5） |
| `pcb_PrimitivePad/Via/Line/Arc/Polyline/Fill.create` 实参顺序 | 与 `@jlceda/pro-api-types` 声明一致；按插件真实调用建图元后读回数值/图层/阻焊**完全一致**（两版均通过） |
| V4 `lib_Footprint.create` / `lib_Symbol.create` 形参 4→6 / 5→6 | 新增参数都在**末尾**（`otherProperty`/`model3D`），现有位置调用不受影响 |
| `sch_Document.importChanges` V4 新增 `force` 参数 | 默认 `false`，与原行为一致 |
| 网表 V4 新格式 `{version, projectId, components, designRule...}` | `getComponentsContainer` 已正确剥壳；`ImportBom`/`ModifyNet`/`ClearEmptyProperties`/`InADNetlist`/`GenerateNet` 都写回**整个对象**，包装不会丢 |
| V4 引脚结构从 `pins` 改为 `pinInfoMap` | `GenerateNet`、`ModifyNet`、`OutPinNet`、`InADNetlist`、`CodeConvert` 均已适配（`OutPinNet` 还做了一层归一化） |

## 七、优化建议（按 ROI 排序）

1. **转换循环批量化**：`PadViaConverter` / `WireConverter` / `RegionImageConverter` 都是「逐条 `await create` + 逐条 `delete`」。上千图元时往返开销占大头；可按 100~200 一组并发（`Promise.all` 分批），并用返回值统计成功数。
2. **统一日志出口**：当前仍有 **198 处** `console.*`（`GenerateNet` 最多），建议 `common.js` 加 `logger`（带 `debug` 开关，生产静默），优先清 `GenerateNet` / `ReplaceComponent`。
3. **空 catch 治理**：**23 处**空 `catch {}`（`GenerateNet` 7、`ReplaceComponent` 5、`EDABridge` 4）。`EDABridge` 那 4 处会让「整块功能失败但界面无提示」，至少补 `logger.warn` + toast。
4. **`alert` → toast**：仍有 **7 处**（`OutPinNet` 4、`NetlistUpdate3DModels` 2、`ClearEmptyProperties` 1），`alert` 会阻塞 iframe 且与 EDA 主题割裂。
5. **`innerHTML` 审计**：**60 处**，其中拼接工程数据（位号、器件名、网络名、工程名）的十几处要确保走 `WolfCommon.escapeHtml`（v1.17.3 已统一实现，但要防回退）。
6. **校准页加约束**：`APITest` 的倍率输入应限制范围（如 0.1~10，角度 0.5~2）并显示「当前值会被谁使用」，从源头避免 P1-3 这类「一次误校准，所有转换全歪」。
7. **V4 新能力可用起来**：`dmt_EditorControl.waitForDocumentReady` / `getDocumentReadyState`（V4 独有）可以替掉现在的固定 `delay(1000)`；`pcb_Document.convertCanvasOriginToDataOrigin` 可用于坐标原点非零的场景。
8. **测试补盲区**：`WireConverter` 的 Region 分支、`PadViaConverter` 的「先建后删」顺序、`getNetlist` 的空文件分支、以及「写回后 POURED 行不减少」都还没有用例——本报告里的 P0-3/P0-4/P1-6 都是这类空白处的缺陷。
9. **桥工具**：多客户端（P2-5）+ 把本次用到的探针沉淀进 `tools/eda-bridge/probes/`（建议新增 `11-pad-via-contract.js`、`12-source-roundtrip.js`），下次版本升级可直接回归。
