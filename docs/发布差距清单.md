## 二、阻塞项（4 条）

### B1. 仓库没收尾：1 个文件未提交、35 个提交未推、没有版本 tag

**证据**

```
modified:   iframe/About.html          ← 未提交
Your branch is ahead of 'origin/main' by 35 commits.   ← 未 push
git tag -l  →  狼黑工具                  ← 只有 1 个非版本号 tag
```

**风险**：扩展广场的源码链接指向 GitHub。现在 GitHub 上的代码比本地落后 35 个提交，
别人点「源码」看到的还是几天前的版本；出问题也无法用 tag 定位到具体发布点。

**做法**：提交 `About.html` → push → `git tag v1.21.0` → push tag。

**验收**：`git status` 干净；`git log origin/main..HEAD --oneline` 为空；`git tag -l 'v1.21.*'` 有结果。

---

### B2. `engines.eda: "^2.2.45"` 在版本语义上不覆盖 V3 / V4

**证据**：官方配置文档写明 `engines.eda` 是「扩展适配的 EDA 版本」，默认值是 `^3.2.0`，
即按语义化版本范围解析。`^2.2.45` 等价于 `>=2.2.45 <3.0.0`，**不包含 3.x 与 4.x**。
而 README、关于页、功能表全部声明「适用 V2.2 ~ V4」。

**风险**：现在能装（平台大概只做提示不做拦截），但上架后审核或后续版本可能按这个字段判兼容，
V3 / V4 用户会被提示「不兼容」——而这正是主力版本。

**做法**：改成 `">=2.2.45"`（覆盖 2.2.45 及之后所有版本）；如需排除未验证的未来大版本，用 `"^2.2.45 || ^3.0.0 || ^4.0.0"`。

**验收**：改后重新出包，扩展管理器在 V4 上安装无兼容性提示；`npm test` 仍绿。

---

### B3. 写盘类功能没有自动备份

**证据**：全项目 `grep "backup"` 在 `src/js`、`iframe/js/src` 下 **0 处**。只有内存级回滚
（同一次操作内失败才还原），关窗或「成功但结果不对」都无法恢复。

**风险**：V4 整份写回会丢铜皮的填充缓存（已知未解）。用户在「生成物理网络（源码方式）」
「从 PCB 转原理图」之后发现铜皮没了，只能靠 README 里那句「请先备份」自救。

**做法**：4 个整份/批量写盘功能执行前，把当前网表或源码原样落一份到用户可见的位置，
提示里给出路径。改动量约 1 天。

**验收**：故意制造写入后异常，用户能凭备份在 3 步内还原；备份名含时间戳，不覆盖旧备份。

### B4. 两条只能人工做的验证

| 项 | 现状 | 为什么不能自动 |
| :--- | :--- | :--- |
| **V3 上的三条写盘流程** | `V4回归记录.md` 只有 V4.1.78 的记录 | 桥能读写源码，但点不了界面按钮 |
| **工时报告在真断网机器上打开** | 只用 headless Chrome 拦截过外部请求 | 拦截验证的是「不发请求」，不是「另一台机器上真能看」 |

**做法**：V3 跑一遍三条流程并追加到 `V4回归记录.md`（改名或加一节「V3 验证」）；
把导出的 html 拷到另一台断网电脑（或手机）打开，确认图表与明细都在。

**验收**：两条各留一条记录/一张截图。

## 三、建议项（6 条，不阻塞 GA）

| # | 项 | 实测 | 影响 | 建议 |
| :-: | :--- | :--- | :--- | :--- |
| S1 | **无 CI** | `.github` 不存在 | 门禁只在本地生效，push 坏了没人拦 | 三步流水线：`npm ci` → `npm test && npm run test:samples` → `npm run build` 并上传 `.eext`。本地全跑一遍才 30 秒 |
| S2 | **多语言空壳** | `locales/{zh-Hans,en}.json` 各 **2 个顶层键**，包内照发 | 英文用户装完看到全中文；审核可能认为「声称支持英文」 | 二选一：补齐，或删掉 `locales/en.json` 只留中文 |
| S3 | **无覆盖率** | 无 `c8`/`nyc` | 改了核心逻辑无法判断哪块没测到 | `c8 node --test`，先记当前值为基线，只允许升 |
| S4 | **商店素材缺 banner** | 只有 576×576 logo；`info.png` 是 2016×648（3.11:1） | 官方要求 banner **64:27 JPEG**，商店页展示位会空着 | 做一张 1920×810 左右的 JPEG banner；再准备 5~6 张功能截图（`docs/商店文案.md` 已列清单） |
| S5 | **包体积 1.45 MB，echarts 双份** | `iframe/js/echarts.min.js` **1.51 MB** 原始 + `WorkingHours.js` 内嵌 gzip **519 KB base64** | 用户下载与安装略慢；两处都要维护 | 页面仍需直接引 echarts（首屏快），报告需内嵌（离线可用），双份有合理性。想减可以只保留内嵌、页面改成解压后再画，但会牺牲工时页首开速度——不建议现在动 |
| S6 | **无诊断信息导出** | 无 | 用户报「点了没反应」时只能靠口述 | 加一个「导出诊断信息」：版本、当前文档类型、最近 50 条日志。比做远程上报更符合本地工具的定位 |

## 四、按顺序的发布动作

### 今天（内部分发就绪）

1. `git add iframe/About.html && git commit`
2. 改 `extension.json` 的 `engines.eda` 为 `">=2.2.45"`（B2）
3. `npm test && npm run build`（约 40 秒）
4. `git push` + `git tag v1.21.0` + `git push --tags`
5. 把 `build/dist/wolfblack-tool_v1.21.0.eext` 发给试用的人

### 上架前（约 1.5 天）

6. V3 三条写盘流程验证，补进 `V4回归记录.md`（B4 上半）
7. 工时报告在真断网设备上打开一次（B4 下半）
8. 写盘自动备份（B3，约 1 天）
9. 接 CI（S1，约 1 小时）
10. 补 banner 与截图（S4，需要设计素材）
11. `locales` 做决策（S2，10 分钟）

### 上架当天

12. 按 `docs/发布检查清单.md` 走一遍「装包实机验证」（干净环境）
13. 用 `docs/商店文案.md` 的文本填商店
14. 发布后打 tag 备注 + 观察首批反馈
